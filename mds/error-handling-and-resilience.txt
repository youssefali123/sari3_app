1. ERROR TRANSLATION — RESOLVED DESIGN, DO NOT REOPEN
==================================================
Principle: presentation never parses strings and never shows error.message.
- Infrastructure classifies backend errors and throws typed errors. The classifier inspects PostgREST/Postgres codes (SQLSTATE + the exception message prefix) and the network failure shape. It lives next to supabase.ts (infrastructure), because it depends on Supabase error shapes.
- Most server exceptions arrive as P0001 with the message equal to a code ("STORE_CLOSED"); some carry a suffix after a colon ("ORDER_CANNOT_BE_CANCELLED: ..."), and some use plain English text ("Driver already has an active order", 23505). Match the prefix/SQLSTATE, never the whole message. Do NOT edit any RPC body (claim_order, release_order, advance_order_status, cancel_order...) to unify messages.
- Generic kinds in shared (pure TypeScript, no business logic): network, session_expired, permission_denied, unexpected.
- Business kinds in each feature's domain, following the AuthErrorType { kind } pattern: orders (store_closed, store_not_found, address_not_found, product_unavailable, product_variant_required, addon_unavailable, coupon_* variants, order_cannot_be_cancelled, order_state_changed, missing_idempotency_key...), driver fulfillment (already_has_active_order, order_not_assigned, invalid_transition, release_reason_required, order_status_changed...). Propose the final lists in contracts/ for my review.
- Structured results that are not exceptions stay structured and also get Arabic messages in the UI: claim_order {claimed:false}, advance_order_status {success:false, error:'ORDER_STATUS_CHANGED'}, validate_coupon {is_valid:false, rejection_reason}, get_order_driver_info NULL.
- Suggested classification (verify against the live function bodies): user-actionable business errors (STORE_CLOSED, PRODUCT_UNAVAILABLE, ADDON_UNAVAILABLE, COUPON_*, ADDRESS_NOT_FOUND, ORDER_CANNOT_BE_CANCELLED); state-changed conflicts that should trigger a refetch (ORDER_STATUS_CHANGED, ORDER_STATE_CHANGED, ORDER_NOT_ACTIVE_OR_NOT_ASSIGNED, ORDER_NOT_FOUND_OR_NOT_ASSIGNED, 23505 "Driver already has an active order", claimed:false); auth (AUTH_REQUIRED, NOT_AUTHENTICATED, expired JWT); permission (ONLY_*, 42501 variants); should-never-reach-the-user (invalid transition trigger, orders_column_guard, MISSING_IDEMPOTENCY_KEY, PRODUCT_VARIANT_REQUIRED) which map to the generic unexpected message.
- Verify empirically, do not assume: what supabase-js actually returns for (a) airplane mode, (b) an expired/invalid token, (c) permission denied, (d) a business exception. Record the observed shapes in the contract.
- Arabic messages: one centralized dictionary per feature keyed by error kind, plus shared generic messages. No inline strings in components. Match the existing copy tone (short, Modern Standard Arabic, says what happened and what to do next). Structure the dictionaries so another locale can be added later; do NOT introduce an i18n framework in this feature.
- Replace every raw error.message display with the dictionary lookup, using the existing shared error component where a full-screen/inline error state is needed. In development only, log the raw error to the console. No remote error-reporting service in this feature.

2. NETWORK AND FOREGROUND WIRING — RESOLVED, DO NOT REOPEN
==================================================
- Wire TanStack Query's onlineManager to the real connectivity signal and focusManager to AppState, in app-level setup under shared/lib. shared/ must not import from features/drivers: use expo-network directly or move the existing service to a shared location (decide in planning, justify). Treat an unknown reachability value (null/undefined) as online; never block on unknown.
- Enable refetchOnWindowFocus (it only works through focusManager); the existing staleTime of 30s limits refetch frequency.
- CRITICAL SIDE EFFECT: once onlineManager reflects reality, TanStack's default networkMode ('online') PAUSES mutations fired while offline and runs them automatically when connectivity returns. For writes (placing an order, claiming, cancelling...) that is wrong: the user would see a stuck spinner and the write could fire minutes later unexpectedly. Set mutations' networkMode to 'always' so writes execute immediately and fail fast with a classified network error. Queries keep the default (paused while offline, cached data stays visible).
- A data screen that has no cached data while offline must show an explicit offline state with a retry action, not an endless spinner (use fetchStatus === 'paused' + no data).
- If supabase.auth.startAutoRefresh()/stopAutoRefresh() is not tied to AppState (Supabase's React Native guidance), add it. If auth refresh fails and the session is lost, reuse the existing sign-out sequence (cache clearing etc.), return to guest browsing, and show one clear "session expired, please sign in again" message; a protected action in progress goes through the existing useRequireAuth flow. Confirm every step of the sign-out sequence tolerates an already-invalid session (e.g. push-token deactivation cannot assume a valid session).

3. WRITES WITH UNKNOWN OUTCOME — RESOLVED, DO NOT REOPEN
==================================================
Rule: a network error on a write means the outcome is UNKNOWN. The UI must not claim definitive failure, and must reconcile against server truth.
- On a network-kind error from any mutation, invalidate the related queries so the screen shows the real state.
- place_order: the previous feature made re-tapping safe (same idempotency key). The message must say the connection failed and that retrying will not duplicate the order. Also invalidate the orders list so an order that was actually created appears.
- claim_order: if the response is lost and a retry returns "already has an active order" (23505), that can be a success in disguise. After a network error or a 23505, refetch the driver's active order and reconcile: if the order is now the driver's active order, show it instead of an error.
- cancel_order / release_order / advance_order_status: a second attempt after a lost success returns a terminal-state conflict (ORDER_CANNOT_BE_CANCELLED, ORDER_NOT_ACTIVE_OR_NOT_ASSIGNED, ORDER_STATUS_CHANGED). Treat these state-changed kinds as "refetch and show current state", with a calm message, not an error dialog.
- decline_order and toggle_driver_availability are already idempotent; they only need the network-error handling.
- Do not add client-side retry loops, background queues, or offline write queues (offline-first is out of scope).

4. REALTIME RECOVERY — RESOLVED, DO NOT REOPEN
==================================================
Supabase Realtime does not replay events missed while disconnected, so the only recovery is to refetch authoritative state.
- Every realtime subscription must observe channel status (SUBSCRIBED / CHANNEL_ERROR / TIMED_OUT / CLOSED). When a channel returns to SUBSCRIBED after having been disconnected or errored, it must trigger a refetch of the related queries. Do not rely on replaying events.
- Keep this behind the existing domain interfaces (OrderRealtimeService, DriverRealtimeService): no Supabase channel-status types in Domain or Application. Expose the concept as a domain-level "connection restored" signal (or have the infrastructure invoke the existing refetch callback), decide in planning and justify.
- Before designing, verify empirically what the client does on a disconnect (toggle airplane mode with an order-detail screen open): does it rejoin by itself, or must the channel be re-created? Design for the observed behavior. Make sure channels are removed on unsubscribe and no duplicate channels leak across reconnects.
