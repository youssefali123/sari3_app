### 1. Fix notification event idempotency

The current T008 says:

`dedupe_key = order_id:event_type:1 + count of existing rows for that order`

Do NOT use `COUNT(*)` or another race-prone derived ordinal to generate dedupe identities.

Replace this with a stable event/transition identity that is guaranteed to be unique for the actual order status transition.

Requirements:

* Repeated trigger execution for the same logical transition MUST resolve to the same dedupe identity.
* Concurrent executions MUST NOT be able to create duplicate logical notification events.
* Database uniqueness MUST enforce the invariant.
* `released` MUST support multiple legitimate release cycles for the same order.
* Do NOT use `UNIQUE(order_id, event_type)` because the same order may legitimately emit `order_released` more than once.
* Use the existing schema/model from `data-model.md` if it already provides a transition/event identity.
* If the current schema does not provide one, explicitly add the minimum DB mechanism required to generate a stable per-transition identity. Do not invent a client-generated ID.
* Update `data-model.md`, contracts, and affected tasks if this requires a schema change.

### 2. Clarify notification_events responsibility

`notification_events` represents durable notification events, not a precomputed permanent recipient list.

The Edge Function MUST resolve recipients server-side at dispatch time.

For customer lifecycle events:

* Resolve the order customer server-side.
* Resolve that customer's active device tokens.
* Respect each device's captured locale.

For `new_order_pool` / `order_released`:

* Resolve eligible drivers server-side at dispatch time.
* Eligibility must follow the existing driver availability/business rules.
* Only active push tokens for currently eligible drivers are targeted.
* The push notification MUST NOT grant ownership of the order.
* `claim_order()` remains the authoritative mechanism for winning an order.

Review whether `target_user_ids UUID[]` is actually needed. If it is not required by the approved design, remove it from the task/schema instead of storing stale recipient information.

### 3. Preserve release semantics

Make the release flow explicit:

accepted/assigned
→ driver releases according to the existing business rules
→ order returns to the available pool
→ exactly one `order_released` notification event for that release transition
→ eligible available drivers are resolved
→ pool push is sent.

If the same order is released again later, that is a new legitimate release transition and MUST produce a new event.

Do not deduplicate all releases for an order into one lifetime event.

Also ensure the trigger cannot emit both duplicate lifecycle events and duplicate pool events for the same transition.

### 4. Clarify trigger behavior

T008 must explicitly state:

* Trigger executes AFTER INSERT OR UPDATE only as required by the actual order lifecycle.
* Status transition detection uses `OLD.status IS DISTINCT FROM NEW.status` for UPDATE.
* INSERT + `pending` produces `new_order_pool` exactly once.
* `active → pending` produces the appropriate release event according to the existing 003 design.
* Trigger performs NO HTTP requests.
* Trigger performs NO Expo API calls.
* Trigger only persists durable notification event records.
* Notification event insertion must be protected by database uniqueness/idempotency.

Do not duplicate or reinterpret the business rules from the existing 003 implementation.

### 5. Clarify Edge Function claiming

Review T018.

The atomic dispatch claim must be implementable using the actual Supabase/Postgres access pattern.

The requirement is:

* Only one concurrent invocation can transition an event from `pending` to `processing`.
* A repeated webhook delivery must safely exit without sending another notification.
* The claim operation must be atomic.
* The implementation must use an appropriate server-side Supabase/Postgres mechanism rather than leaving raw pseudo-SQL that cannot be executed by the chosen client API.
* If necessary, define a small server-side SQL/RPC helper for atomic claiming, but avoid unnecessary abstraction.

Do not introduce a general queue/message-broker system.

### 6. Keep webhook architecture

Preserve this exact high-level pipeline:

`orders transition`
→ `Postgres trigger`
→ `notification_events`
→ `Supabase Database Webhook`
→ `notify-order-status Edge Function`
→ `Expo Push API`
→ target device tokens

The Postgres trigger MUST NOT make HTTP requests.

The Database Webhook is the asynchronous boundary between the database transaction and push dispatch.

### 7. Preserve RLS/security requirements

Verify T006, T007, and T014.

`device_push_tokens`:

* RLS enabled.
* Authenticated users can access only their own rows.
* No cross-user INSERT/UPDATE/SELECT.
* Anonymous access denied.
* No client DELETE policy unless explicitly required.

* Never expose `service_role` in `src/`.

`notification_events`:

* RLS enabled.
* No normal authenticated/anonymous CRUD policies unless explicitly required.
* Client cannot directly manipulate notification events.
* Edge Function uses the appropriate server-side privileged access.

Verify that the SQL privileges are consistent with the project's existing migration/grant discipline.
